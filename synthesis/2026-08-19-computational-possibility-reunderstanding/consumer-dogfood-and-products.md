# CP Consumer Dogfood and Research Product Topology

## 1. Product contraction

An initial list of many apparent CP outputs was deliberately contracted to four first-class families:

`Situation Analysis -> Local Possibility Analysis -> Comparative/Transport Analysis -> Applicability Analysis`.

This is a classification of research outputs, **not** a mandatory workflow.

### Situation Analysis

Question: `What exactly is the computational claim?`

Main value: prevent underconstituted questions from receiving false possibility/impossibility answers.

### Local Possibility Analysis

Question: `What is possible here?`

Includes exact-scope achievability/impossibility, successful witness families, resource-constrained feasible regions/frontiers and lower-bound guards.

### Comparative / Transport Analysis

Question: `What changes, refines, substitutes or transports if the situation/capability changes?`

Includes regime comparison, reduction/hardness, capability substitution, composition, presentation transport and quantitative theorem transfer.

It must keep distinct:

- contract demand;
- provider guarantee;
- client robustness;
- regime power;
- reduction/hardness;
- resource/performance order.

### Applicability Analysis

Question: `What does the formal result license us to say about this external target now?`

Uses the existing five-block bridge:

`ClaimScope + TargetScope + TransportBurden + PremiseEvidence + Verdict`.

Current Harness source was revalidated at:

The useful seam was `HarnessProviderUsePolicy` plus Campaign-5 provider-route preservation evidence.

1. `C_policy(U,R)` — route admitted under exact use-policy contract;

- `SameUsePolicyAdmission != CapabilitySubstitutability`;

- `EndpointCoAdmissibility != DirectionalTransitionPreservation`.

Owner seam:

- Harness owns exact actual composition/admission/provider construction;
- CP owns whether the admitted replacement preserves the higher-level computational contract required by the consumer.

This is a real independent CP responsibility, not something Harness should expand to own.

## 3. Runtime / Interlocus applicability dogfood

A live 2026-08-19 Workstation observation found:

- anchor `surf-clash` unavailable at that observation;
- scoped egress profile `finance-okx` non-listening/inactive/without eligible member at that observation;
- an independent Runtime loopback probe corroborated failure to connect to the exact loopback listener;
- a separate pure-local Runtime computation witness succeeded.

The observation is time-sensitive and is **not** preserved here as current operational truth. The durable value is the inference structure it tested.

Three scoped conclusions diverged:

### Narrow constructive case

One implemented actual witness can support a narrow `APPLIES` verdict for the exact target/configuration it realizes.

### Exact route-dependent constructive case

If a formal witness requires the unavailable exact egress capability, current owner evidence blocks `APPLIES`; an earlier applicability basis may become `EXPIRED` after currentness drift.

### Broad impossibility case

`exact route unavailable` does not imply `all actual routes impossible`.

To transport formal impossibility/lower bounds to an actual system, CP needs actual-to-formal coverage/reflection over every relevant actual candidate class.

Therefore the broad system-wide claim remained `UNRESOLVED`.

Permanent controls:

- `HistoricalCapability != CurrentCapability`;
- `ExactRouteUnavailable != GlobalNetworkImpossibility`;
- `OneRouteFailure != ActualCandidateCoverage`.

## 4. Constructive / negative applicability asymmetry

The real dogfood made a key derived law operationally intuitive:

### Constructive / upper

To show actual achievability:

`formal witness -> actual witness`.

For quantitative upper claims, add upper domination relating formal performance/resource semantics to actual measurements.

### Impossibility / lower

To show actual impossibility:

`relevant actual candidate witness -> formal witness`.

For quantitative lower claims, add lower reflection so a hypothetical too-cheap actual witness would contradict the formal lower bound.

Thus:

`FormalToActualImplementability != ActualWitnessCoverage`.

One success can prove a narrow existence claim; one failure cannot prove global non-existence.

## 5. CP's practical owner niche

The two heterogeneous consumer cases support a common description:

> CP acts as a **computational inference firewall** against scope inflation across owners.

It blocks unsafe leaps such as:

- Harness admission -> capability equivalence;
- Runtime execution -> uniform achievability theorem;
- Interlocus route failure -> global computational impossibility;
- SCD semantic equivalence -> computational equivalence;
- historical capability -> current applicability.

This is why CP has a stable independent project niche even when many mathematical ingredients are known in specialist fields.
