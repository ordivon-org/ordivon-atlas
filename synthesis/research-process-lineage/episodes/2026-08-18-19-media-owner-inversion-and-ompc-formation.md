## Question

After the Media research programme had reached strong Foundation closure, what project should actually own the resulting semantics, how should Studio/Web/Game be related to it, and what—if anything—should become shared Media implementation?

## Initial position

The physical/project identity was still Ordivon Studio. Media research lived inside the Studio repository, and an intuitive product taxonomy still pulled toward writing/image/audio/video/interactive/3D plus Studio/Web/Game-like surfaces.

A natural first project interpretation was therefore close to:

```text
Studio
  -> Media capabilities
  -> perhaps Web / Game / other realization surfaces
```

This was reasonable historically because the repository and existing production tooling were Studio-first, and M7 consumer/production work had been the practical entrance into the domain.

## Pressure that broke the Studio-first interpretation

Re-reading MF0–MF9 and the destructive Round B/D results showed that Media's actual responsibility was much broader than creative production:

- structured mediation;
- signal/perception/representation;
- composition;
- mediated space/time;
- state/dynamics;
- agency and experience structure;
- derived publication/exposure/identity/translation/preservation/interface/presence/datafication relations.

Studio could consume and construct these structures, but could not plausibly own the whole semantic domain.

The decisive distinction became:

`Media != Studio` and `Studio = Media authoring/production capability plane`.

## Rival / rejected project shapes

### Rival A — keep Studio as top-level owner

Rejected because it implies Studio owns Media phenomena that exist outside authoring/production, including publication standing, mediated presence, interface relations, infrastructure roles and datafication/legibility.

### Rival B — rename Studio to Media and delete Studio

Rejected because Studio remains a real capability identity with durable production models, CLI/package/tool names and Art & Expression work.

### Rival C — Media owns Web

Initially plausible because Web realizes nearly the entire Media stack. Later narrowed: Web is a general Ordivon-facing realization/interaction system serving many owners, so making it a Media semantic child would create a new ownership distortion.

### Rival D — Game is Interactive Media and should be absorbed

Rejected strongly. Game owns ludic constitution/action/challenge/mastery/case semantics. Media owns their mediation. A Game can survive radically different media realizations; interactive media need not be Game.

### Rival E — promote important Round-B/D candidates to MF10

Rejected repeatedly. Importance/frequency/product centrality did not establish irreducible Foundation responsibility.

## Revision 1 — project owner inversion

The project relation was inverted:

```text
old: Studio project containing Media research
new: Media project containing Studio capability
```

This was materialized physically during M0/M1:

`/root/projects/ordivon-studio -> /root/projects/ordivon-media`.

The migration deliberately preserved `ordivon-studio` capability identities and did not globally rewrite historical/evidence paths or absorb Web/Game.

## Revision 2 — Derived Media becomes a positive architecture result

The failure of Communication, Protocol, Publication, Interface, Presence, Datafication and many other candidates to become MF10 was reinterpreted as successful explanatory compression rather than missing ontology.

Surviving law:

`NONPRIMITIVE != UNREAL`.

Media therefore acquired a two-level explanatory shape:

```text
MF0–MF9 foundation substrate
+ first-class Derived Media relations
+ typed cross-owner bridges
```

rather than a flat growing list of primitives.

## Revision 3 — from theory to projection discipline

The project then asked what Media could do across Ordivon without creating a universal framework.

The answer emerged around source-owned truth being projected to humans/Agents:

`SourceTruth -> MediaProjection -> Observer`, while preserving `Projection != SourceAuthority`.

This motivated the technology-neutral OMPC-v0 reference contract rather than an immediate SDK/runtime/schema.

## Hostile dogfood sequence

### Fixture A — Host

A single Host Task revision was projected differently to Human/Web and Agent observers. When Host advanced from revision 3 to 4, the old projection became source-fenced historical relative to Host progression without Media inferring Runtime/Git/domain staleness.

Surviving pressure:

- authority conservation;
- observer relativity;
- omission disclosure;
- currentness non-fabrication;
- action exposure != execution.

### Fixture B — Studio

A real SVG -> PNG Production lineage was used. Exact rerender reproduced the selected PNG bytes; adding a non-visual XML comment changed source Blob identity while retaining byte-identical output. PNG also discarded SVG editable structure.

Revision forced:

`Identity Non-Collapse`.

This distinguished historical source identity, semantic Production/Asset identity, exact Blob identity, realization relation and current recovery locator.

### Fixture C — Web

A real Chromium interaction fixture kept source proposition, operation identity and initial/final states constant while changing transient feedback trajectories. Defective `premature-success` and `silent-delay` encounters collapsed to the same initial+final ablation.

Revision forced:

`Temporal Coverage Non-Collapse`.

Same endpoints did not establish same encounter.

### Fixture D — Finance

Finance QB6 kept headline performance/attribution metrics constant across two turns while new execution-suitability evidence changed the owner disposition from `more_research` to `no_op`.

Revision forced:

`Metric / Proxy Non-Collapse`.

A numerically true metric surface can remain semantically insufficient for the decision-facing task.

## Surviving insight

The strongest evidence was not that OMPC accumulated more objects. Across heterogeneous dogfood, the original six semantic roles survived while the invariant set became more precise.

This supported OMPC as a shared **reference/conformance discipline**, but not shared implementation.

The critical distinction became:

`RepeatedSemanticPressure != RepeatedImplementationMachinery`.

## Final revision — stop construction by default

After M4, the remaining temptation was to continue with Fixture E/F/G, Game, Runtime, Atlas and a Media SDK/runtime.

The Phase-1 audit rejected that roadmap-by-symmetry.

The project closed Phase 1 with posture:

`STABLE_OWNER / CONSUMER_PRESSURE_DRIVEN`.

New construction now requires concrete evidence: a failing consumer, missing Derived relation, repeated implementation duplication, real Studio production constraint or Foundation-level counterevidence.
